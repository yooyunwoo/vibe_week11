# 저장소를 localStorage에서 Turso로 바꾸기

## Problem Statement

지금은 Todo와 카테고리가 브라우저의 localStorage에만 저장된다. 그래서 그 브라우저에서만 보이고, 폰과 PC에서 같은 목록을 볼 수 없으며, 브라우저 데이터를 지우면 모두 사라진다. 처음부터 "나중에 Turso 데이터베이스로 바꿀 수 있게" 해 두었으므로 이제 실제로 바꾼다.

## Solution

Todo와 카테고리를 Turso(클라우드 SQLite 호환 데이터베이스)에 저장한다. 사용자가 보는 화면과 동작은 그대로이고, 어느 기기에서 열어도 같은 목록이 보인다. 데이터베이스 접속 정보는 서버에만 두고 브라우저에는 노출하지 않는다. 배포하더라도 아무나 데이터를 바꿀 수 없도록 간단한 접근 보호를 둔다.

## User Stories

1. As a 사용자, I want 어느 기기에서 열어도 같은 할 일 목록이 보이기를, so that 폰과 PC를 오가며 쓸 수 있다
2. As a 사용자, I want 브라우저 데이터를 지워도 할 일이 사라지지 않기를, so that 실수로 잃어버리지 않는다
3. As a 사용자, I want 화면과 동작이 지금과 똑같기를, so that 저장소가 바뀌어도 다시 배울 것이 없다
4. As a 사용자, I want 할 일 추가, 완료 토글, 삭제, 완료한 일 지우기가 그대로 동작하기를, so that 매일 쓰는 기능이 깨지지 않는다
5. As a 사용자, I want 제목 수정과 카테고리 변경이 그대로 동작하기를, so that 기존 기능을 계속 쓸 수 있다
6. As a 사용자, I want 카테고리 만들기와 삭제가 그대로 동작하기를, so that 분류를 계속 관리할 수 있다
7. As a 사용자, I want 카테고리를 삭제해도 그 안의 할 일이 지워지지 않고 미분류가 되기를, so that 저장소가 바뀌어도 이 약속이 지켜진다
8. As a 사용자, I want 카테고리 이름의 공백 제거, 빈 이름과 중복 이름 거부 규칙이 그대로이기를, so that 규칙이 저장소에 따라 달라지지 않는다
9. As a 사용자, I want 새로고침해도 방금 한 변경이 남아 있기를, so that 저장이 믿을 만하다
10. As a 사용자, I want 데이터를 불러오는 동안 "할 일이 없어요" 안내가 잠깐 보이지 않기를, so that 네트워크가 느려도 화면이 거짓말하지 않는다
11. As a 사용자, I want 인터넷 연결이 끊기거나 데이터베이스가 응답하지 않을 때 무엇이 잘못됐는지 알려 주기를, so that 데이터가 사라진 것으로 오해하지 않는다
12. As a 사용자, I want 저장에 실패했을 때 변경이 된 것처럼 보이지 않기를, so that 화면과 실제 데이터가 어긋나지 않는다
13. As a 사용자, I want 목록이 지금처럼 오래된 것부터 정렬되기를, so that 순서가 갑자기 바뀌지 않는다
14. As a 사용자, I want 존재하지 않는 항목을 수정하거나 삭제해도 오류 없이 넘어가기를, so that 다른 기기에서 이미 지운 항목 때문에 화면이 멈추지 않는다
15. As a 사용자, I want 필터(상태, 카테고리)는 여전히 저장되지 않고 "전체"로 시작하기를, so that 기기마다 보는 방식이 독립적이다
16. As a 사용자, I want 내 데이터에 나만 접근할 수 있기를, so that 주소를 아는 다른 사람이 내 할 일을 보거나 바꿀 수 없다
17. As a 사용자, I want 접근 암호를 한 번 입력하면 그 기기에서 계속 쓸 수 있기를, so that 매번 입력하지 않아도 된다
18. As a 사용자, I want 암호를 모르는 사람의 요청이 모두 거부되기를, so that 화면을 거치지 않은 직접 요청도 막힌다
19. As a 개발자(나), I want 데이터베이스 주소와 비밀 키가 코드나 GitHub에 올라가지 않기를, so that 공개 저장소여도 안전하다
20. As a 개발자(나), I want 접속 정보가 없을 때 앱이 무엇이 빠졌는지 알려 주기를, so that 설정을 빠르게 고칠 수 있다
21. As a 개발자(나), I want 데이터베이스 표(테이블)를 한 번의 명령으로 만들 수 있기를, so that 새 환경도 쉽게 준비할 수 있다
22. As a 개발자(나), I want 같은 동작 테스트를 인터넷 없이 로컬 데이터베이스로 돌릴 수 있기를, so that 테스트가 빠르고 안정적이다
23. As a 개발자(나), I want 화면 코드가 저장소 종류를 몰라도 되기를, so that 나중에 저장소를 또 바꿔도 화면은 그대로다
24. As a 개발자(나), I want 이번 선택의 이유가 문서(ADR)로 남기를, so that 나중에 왜 이렇게 했는지 알 수 있다
25. As a 기존 사용자, I want 이 브라우저에 저장해 둔 할 일과 카테고리를 새 저장소로 가져올 수 있기를, so that 전환해도 쌓아 둔 목록을 잃지 않는다
26. As a 기존 사용자, I want 가져올 데이터가 있을 때만 가져오기 안내가 보이기를, so that 데이터가 없는 기기에서는 화면이 복잡해지지 않는다
27. As a 기존 사용자, I want 가져오기 전에 몇 개를 가져올지 알려 주기를, so that 무엇이 옮겨지는지 확인하고 결정할 수 있다
28. As a 기존 사용자, I want 가져오기가 제목, 완료 여부, 생성 시각, 카테고리 연결을 그대로 옮기기를, so that 옮긴 뒤에도 목록이 똑같이 보인다
29. As a 기존 사용자, I want 같은 데이터를 두 번 가져와도 중복이 생기지 않기를, so that 실수로 두 번 눌러도 안전하다
30. As a 기존 사용자, I want 카테고리가 없던 시절에 저장된 할 일도 문제없이 가져오기를, so that 오래된 데이터도 빠짐없이 옮겨진다
31. As a 기존 사용자, I want 가져오기가 끝나면 몇 개를 옮겼는지 알려 주기를, so that 성공했는지 확인할 수 있다
32. As a 기존 사용자, I want 가져오기가 실패하면 브라우저의 원래 데이터가 그대로 남기를, so that 실패해도 아무것도 잃지 않는다
33. As a 기존 사용자, I want 가져온 뒤에도 브라우저의 원래 데이터를 자동으로 지우지 않기를, so that 확인이 끝나기 전에는 원본이 남아 있다

## Implementation Decisions

- **저장 모듈의 공개 인터페이스는 바꾸지 않는다.** Todo와 카테고리를 다루는 기존 async 함수들의 이름, 인자, 반환 형태(카테고리 추가의 성공/거부 결과 포함)를 유지한다. 화면과 테스트가 의존하는 경계가 이것 하나이기 때문이다(ADR-0001). 구현만 localStorage에서 데이터베이스로 교체한다.
- **데이터베이스 구조**: Todo 표와 카테고리 표 두 개. Todo는 문자열 UUID `id`, 제목, 완료 여부, 생성 시각(ISO 문자열), 카테고리 `id`(비어 있을 수 있음)를 가진다. 카테고리는 문자열 UUID `id`와 이름을 가진다. ADR-0002에서 정한 대로 Todo의 카테고리 참조는 외래 키이고, 카테고리를 지우면 참조가 자동으로 비워지게(`ON DELETE SET NULL`) 한다.
- **규칙은 저장 모듈에 그대로 둔다**: 제목과 카테고리 이름의 공백 제거, 빈 이름 거부, 이름 중복 검사(대소문자 구분 없음), 없는 항목은 무시, 존재하지 않는 카테고리는 미분류로 취급하는 것. 데이터베이스 제약은 안전망일 뿐 규칙의 출처가 아니다.
- **데이터베이스는 서버에서만 접근한다.** 접속 주소와 비밀 키는 환경 변수로만 받고 브라우저 쪽 코드에 절대 들어가지 않는다. 브라우저의 화면은 서버 함수(Server Action)를 통해서만 저장 모듈을 호출한다. 현재 화면이 저장 모듈을 직접 부르는 구조는 이를 위해 바꾼다.
- **읽기와 쓰기 모두 서버 함수를 거친다.** 화면 로직(필터 계산, 수정 상태 등)은 그대로 브라우저에 둔다. 서버 호출은 비동기이므로 불러오는 중 상태와 실패 상태를 화면이 구분해서 다룬다.
- **실패 처리**: 서버 호출이 실패하면 변경을 화면에 반영하지 않고 사용자에게 알린다. 성공이 확인된 뒤에 목록을 다시 불러온다.
- **접근 보호**: 서버 함수는 화면을 거치지 않은 직접 요청으로도 호출될 수 있으므로, 모든 서버 함수가 요청의 접근 자격을 먼저 확인한다. 로그인 시스템 대신 환경 변수로 정한 암호 하나를 쓰고, 맞으면 그 기기의 브라우저에 보호된 표식을 남긴다. 암호가 설정되지 않은 환경(로컬 개발)에서는 보호를 끌 수 있다.
- **구현 전에 Next.js 문서를 읽는다.** 이 프로젝트의 Next.js 버전은 일반적인 지식과 다를 수 있다고 프로젝트 지침이 경고하고 있고, 캐시 관련 설정(Cache Components)이 켜져 있다. 서버 함수, 데이터 가져오기, 캐싱 문서를 먼저 확인한다.
- **데이터 가져오기**: 이 브라우저의 localStorage에 있는 Todo와 카테고리를 새 저장소로 한 번 옮기는 기능이다. 데이터베이스는 서버에서만 접근하고 localStorage는 브라우저에서만 읽을 수 있으므로, 브라우저 화면이 읽은 데이터를 서버 함수로 보내고 서버가 저장 모듈의 새 "일괄 가져오기" 함수로 저장한다. 이 함수가 이번 작업에서 저장 모듈 인터페이스에 추가되는 유일한 함수다.
- 일괄 가져오기는 `id`를 그대로 유지하고 이미 있는 `id`는 건너뛰므로 여러 번 실행해도 중복이 생기지 않는다(멱등). 카테고리 없이 저장된 옛 Todo와 존재하지 않는 카테고리를 가리키는 Todo는 미분류로 가져온다. 모두 한 번에(전부 성공하거나 전부 실패) 저장해 중간에 실패해도 반쪽 데이터가 남지 않는다.
- 가져오기 안내는 브라우저에 가져올 데이터가 있을 때만 보인다. 가져오기 전에 개수를 알려 주고, 끝나면 옮긴 개수를 알려 준다. 브라우저의 원본 데이터는 자동으로 지우지 않는다.
- **데이터베이스 클라이언트**는 Turso가 제공하는 클라이언트 라이브러리를 쓴다. 같은 클라이언트로 로컬 파일 데이터베이스와 Turso 원격 데이터베이스를 모두 열 수 있어 테스트와 운영이 같은 코드를 쓴다.
- **표 만들기**: 한 번의 명령으로 표를 만드는 스크립트를 둔다. 이미 있으면 건드리지 않는다.
- **ADR-0003**을 새로 쓴다: 저장소로 Turso를 선택하고, 서버에서만 접근하며, 서버 함수를 통해 화면이 호출하는 결정과 이유.
- 용어집은 도메인 용어가 바뀌지 않으므로 수정하지 않는다.

## Testing Decisions

- 좋은 테스트는 내부 구현이 아니라 저장 모듈이 밖으로 보여 주는 동작만 확인한다. 함수를 호출하고 조회 결과를 본다.
- 테스트 경계(seam)는 **기존과 같은 저장 모듈의 async 인터페이스 하나**다. 새 경계를 만들지 않는다.
- 기존 저장 모듈 테스트(Todo와 카테고리의 추가, 수정, 삭제, 규칙, 정렬, 카테고리 삭제 시 미분류, 존재하지 않는 항목 무시 등)를 **그대로 데이터베이스 구현에 대해 통과**시킨다. 동작이 같다는 것이 이 작업의 성공 기준이다.
- 테스트는 인터넷 없이 로컬(메모리 또는 임시 파일) 데이터베이스를 쓰고, 각 테스트는 빈 데이터베이스에서 시작한다.
- 접근 보호는 "자격이 없으면 거부, 있으면 통과"만 확인한다.
- 화면(브라우저) 수준의 자동 테스트는 하지 않는다. 사전 사례(prior art)는 기존 저장 모듈 테스트와 화면용 순수 함수 테스트다. localStorage 전용 테스트 준비물은 localStorage 구현이 사라지면 함께 정리한다.

## Out of Scope

- 로그인 시스템, 여러 사용자, 사용자별 데이터 분리(암호 하나로 보호하는 것까지만 한다)
- 실시간 동기화(다른 기기의 변경이 자동으로 나타나는 것). 새로고침하면 보인다.
- 오프라인 사용, 낙관적 업데이트
- 가져온 뒤 브라우저의 원본 데이터를 자동으로 지우는 것(사용자가 직접 정리한다)
- 가져오기를 되돌리는 기능
- 배포 자체(호스팅 선택과 설정). 배포 시 필요한 환경 변수와 보호만 다룬다.
- 데이터베이스 백업, 모니터링, 요금 관리

## Further Notes

- 가져오기를 하지 않으면 전환 후 처음에는 목록이 비어 있다. 이 스펙에 가져오기가 포함되어 있으므로, Turso에 연결한 뒤 기존 데이터가 있는 브라우저에서 한 번 실행한다.
- 순서: 데이터베이스 구현 → 화면을 서버 함수로 연결 → 접근 보호 → Turso 연결 → 데이터 가져오기. 접근 보호는 반드시 Turso에 연결하거나 배포하기 전에 끝낸다.
- 처음 시작은 파일 하나짜리 로컬 데이터베이스로 모든 것을 확인한 뒤, 마지막에 Turso 접속 정보만 바꿔 끼우는 방식이다. 그래서 Turso 가입 전에도 앞 단계를 진행할 수 있다.
